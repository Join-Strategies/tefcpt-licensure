# Post-mortem: stepper rail line/dot misalignment

**Symptom:** On WP staging, the vertical connector line in the "Your path" rail
was offset ~7px to the right of the step dots (dots sat left of the line).

**Why it matters as a record:** this was a one-line CSS fix that took several
failed rounds. The fix was easy; *finding* it was slow because it was diagnosed
in the wrong environment. This doc captures the trap so the next person skips it.

## Root cause

The rail markup (`#flow-root` / `.lf-*`, generated by `licensure-flow.js`) renders
**inside the Landslide theme's `.prose` container**. The theme bundles
`@tailwindcss/typography`, whose stylesheet includes:

```css
.prose :where(ul > li):not(:where([class~="not-prose"], [class~="not-prose"] *)) {
  padding-inline-start: 0.375em; /* ≈ 9px on our li */
}
```

This matches every `li.lf-step`. The catch is specificity: `:where()` contributes
**zero**, so the whole selector is only `(0,1,0)` — a **tie** with our
`.lf-step { padding: var(--space-1) var(--space-2) }` `(0,1,0)`. On a tie, source
order decides, and the theme CSS loads after ours, so it won.

Result: step `padding-left` was overridden from our intended **16px** down to
**9px**. The connector line (`.lf-steps::before`, fixed at `left: 27px`) stayed
put while every dot shifted 7px left → the visible misalignment.

The base CSS was always correct: with no theme, every dot measured `DELTA = 0px`.
The bug existed **only** under the theme cascade.

## The fix

`public/styles.css` (theme-interop block), mirrored to `plugin/assets/styles.css`:

```css
.lf-steps > .lf-step { padding: var(--space-1) var(--space-2) !important; }
```

`!important` on our **physical** `padding` beats the theme's non-`!important`
**logical** `padding-inline-start`. (The companion `.lf-steps li { padding-left: 0 !important }`
reset and `.lf-steps > .lf-group { ... !important }` rule restore group-label
padding the same way.)

## Why it took so long — the two traps

1. **Diagnosed in the wrong environment.** Early rounds reasoned about CSS math
   and the *theme stripping* padding, then verified against the bare prototype.
   The prototype was always fine. The bug only reproduces with the live theme's
   `.prose` rules in the cascade. **Staring at code can't reveal a cross-stylesheet
   specificity tie — only a measurement in the real environment can.**

2. **A correct fix that never shipped.** A working `!important` fix was written
   locally, but the plugin **version string was not bumped** (`$v` stayed `0.3.5`).
   WPEngine + the browser kept serving the cached old `styles.css?ver=0.3.5`, so a
   "deployed + caches flushed" page still showed the bug. Page-cache flush does
   **not** bust the versioned asset URL.

## What actually solved it (the feedback loop)

Loading the live staging page with the agent-browser (Chrome CDP) flow — the
theming doc already noted Cloudflare blocks plain headless/curl — and running a
measurement script against the **real DOM**:

- read `getComputedStyle(step).paddingLeft` → `9px` (not 16px) ← smoking gun
- compared each `.lf-dot` center to the `::before` line center → `DELTA = -7px`
- enumerated every CSS rule matching `.lf-step` that set padding → exposed the
  `.prose :where(ul>li)` rule and its source file
- injected the candidate fix as a `<style>` and re-measured → `DELTA = 0px` before
  touching any file

## Checklist for the next "simple CSS bug" on WP

- [ ] **Reproduce in the environment the user sees** (live WP via agent-browser),
      not just the Astro prototype. The theme `.prose` cascade changes everything.
- [ ] **Measure, don't theorize.** `getComputedStyle()` + `getBoundingClientRect()`
      on the real DOM beats CSS arithmetic every time.
- [ ] Suspect `@tailwindcss/typography` `.prose :where(...)` rules for any list,
      heading, or spacing oddity. `:where()` = zero specificity = ties you lose on order.
- [ ] When a fix "doesn't work" on staging, **check the served asset version first**
      (`styles.css?ver=…` in the loaded sheet). Bump `$v` in
      `plugin/tefcpt-licensure-page.php` on every asset-changing deploy.
- [ ] Confirm the fix by **injecting it live and re-measuring** before declaring done.
